Mapa del sistema

Cuatro servicios para arrancar, tres para más adelante, dos bases de datos y dos lenguajes en el backend.

Servicios base

Gateway KrakenD
Punto de entrada único. Rutea a cada servicio y valida el token que emite Firebase Auth antes de dejar pasar la request.
Auth Python
La autenticación (login, registro, tokens) corre en Firebase Auth. Este servicio es el dueño del usuario: guarda la cuenta y el perfil (nombre, foto, descripción, estado). Los demás servicios nunca duplican estos datos, solo referencian el user_id.
Servidores y canales Python
Crear servidores, canales, invitaciones, membresías y roles internos de cada servidor. La membresía guarda user_id + rol; el perfil del miembro se resuelve consultando a Auth.
Mensajes Go
Enviar, editar, borrar, historial paginado, adjuntos y reacciones.
Voz Go
Quién está en cada canal, señalización WebRTC y el ruteo del audio.

Más adelante

Métricas Python
Usuarios activos, mensajes por canal, errores y latencia.
Notificaciones Go
Push y mail. Escucha los eventos de Mensajes y Voz.
Monetización Python
Planes, límites por plan y cobros.

Datos

PostgreSQL
Todo lo relacional y con permisos. Auth y Servidores usan la misma instancia pero cada uno es dueño de sus tablas: Auth tiene cuentas y perfiles, Servidores tiene servidores, canales, roles y membresías (que referencian el user_id de Auth, sin duplicar su perfil).
MongoDB
Mensajes. Mucho volumen, forma variable y consultas casi siempre por canal y fecha.

Por qué cada lenguaje donde está

KrakenD

El Gateway no es un servicio a medida: es una API gateway declarativa, configurada por archivo en vez de código propio para mantener.

Valida el token de Firebase Auth en el borde y rutea al resto de los servicios, así ninguno tiene que reimplementar esa verificación.

Firebase Auth

La autenticación (alta de cuentas, login, recuperación de contraseña, tokens) se delega a Firebase Auth en vez de escribirla desde cero.

El servicio Auth propio se queda con lo que Firebase no resuelve, y es el dueño de esos datos: perfil de usuario, cuenta dentro de Discordia. Servidores solo guarda el user_id como referencia — nunca copia el perfil.

Go

Mensajes y Voz. Son las piezas que sostienen miles de conexiones abiertas al mismo tiempo y reparten cada mensaje entre todos los que están mirando el canal.

Las goroutines hacen eso barato y el binario compilado arranca solo, sin runtime alrededor.

Python

Servidores y canales, y después Métricas y Monetización. Es donde hay reglas de negocio, validaciones y permisos: se escribe rápido, se lee fácil y el tráfico es de picos cortos, no de conexiones sostenidas.

FastAPI si querés async y tipos; Django si preferís traer el admin y el ORM ya resueltos.

React Native + TypeScript

Una sola base de código para iOS, Android y web con React Native Web. Los tipos del cliente pueden generarse desde el esquema de la API para que no se desincronicen.

Tailwind en React Native va a través de NativeWind, que traduce las clases a estilos nativos. Las mismas clases sirven en la versión web.

Lo que falta decidir

  1. ¿Arrancar con los dos lenguajes o con uno? Dos backends significan dos toolchains, dos pipelines de CI y dos formas de hacer todo. Una salida es empezar todo en Python y pasar a Go solo Mensajes y Voz cuando el volumen lo justifique.
  2. Dónde vive el estado en vivo. Presencia, typing y quién está en cada canal de voz cambian todo el tiempo y no van a ninguna de las dos bases. Va a hacer falta algo en memoria, tipo Redis.
  3. Voz: SFU propio o proveedor. Montar mediasoup o LiveKit da control y cuesta trabajo; usar un servicio externo te saca el problema de encima y te ata a su precio.
  4. Los mensajes en Mongo necesitan un índice por canal y fecha desde el día uno. Sin eso el historial se vuelve lento apenas crezca.
  5. Cómo se enteran los servicios entre sí. Cuando exista Notificaciones va a necesitar escuchar lo que pasa en Mensajes; ahí conviene una cola en vez de llamadas directas.
